# Try v6.3 in a project

Use a source checkout of this repository at v6.3. The scripts run locally with Bash, Git, and standard Unix tools. Project checks still use the project's own test and build tools.

## Install or update

From this source checkout, point the command at the project:

```sh
project=/absolute/path/to/project
bash scripts/node.sh update "$project"
```

For a project without `.agent/`, initialize it instead:

```sh
bash scripts/node.sh init --preset software-development --mode track-shared "$project"
```

Choose the tracking mode appropriate for the project. Complete the ordinary bootstrap: purpose, guardrails, quality-bar split, routing, and entry-point mirrors.

An update preserves existing rules, docs, memory, learned records, configuration, and the project-owned check driver. A conflicting custom helper using a new managed name stops migration before changes. Reconcile the shorter preset with local rules. Keep project-specific requirements. Refresh entry points from the matching template in this checkout.

## Session-start hook

`init` and `update` wire a session-start hook into Claude Code and Codex. The hook hands the harness the `status.sh --load` output before the first turn. Both entry points skip the load step when the hook's block holds that output.

- The installer needs `python3` to merge the hook into existing settings files. Without it, nothing is written and the snippets to add by hand print.
- Codex runs the hook only after the developer approves it once with `/hooks`. Until then the entry point loads the node.
- Under `ignore-all` the hook goes in personal files that reach no clone and no worktree.
- `status.sh` prints a `HOOK:` line when the output is over the hook's limit. It names the bytes over and the two levers, `TAIL_LINES` and the memory index.
- `bash scripts/node.sh update --hooks none "$project"` removes the hook and records the choice.

See [session-start.md](session-start.md) for the files each tracking mode uses, the limit, and what was checked live.

## Configure checks

The starter `.agent/scripts/checks.sh` fails until configured. Replace its body with named project checks. For a project using Node's built-in test runner, a driver can be:

```sh
#!/usr/bin/env bash
set -u
case "${1:-}" in
  test) exec node --test --test-reporter=tap ;;
  lint) exec npm run lint ;;
  *) echo 'Unknown check' >&2; exit 2 ;;
esac
```

Use the project's real commands. Keep the check names in Project guardrails and the entry point. Updates preserve this driver.

The starter `verify.conf` requires a positive test count for the `test` check. `TEST_COUNT_FORMAT=auto` counts TAP and the closing summary of the runners listed in [verify.md](verify.md). Unknown output remains unknown, and the run is then inconclusive. A node installed before `auto` existed keeps `TEST_COUNT_FORMAT=tap` in its `verify.conf`, which counts TAP alone. Change that line to `auto` by hand, because an update preserves the file.

Set `POSITIVE_TEST_CHECKS` to the checks that require a known positive count. Clearing that list accepts successful command exits without proving tests ran. Such receipts still report an unknown count.

## Prove a change

The software-development preset keeps a test only when it protects a rule that no kept test protects. Everything else is proved with a scratch test in a Git-ignored folder, which does not outlive the task. Name that folder in Project guardrails and in `SCRATCH_DIR` in `review.conf`. See the scratch test fail once, before the change or with the behavior broken by hand, and delete it when the task ends.

## Verify and record

From the target project:

```sh
bash .agent/scripts/checkpoint.sh --checks test \
  --tool <tool> --area payments --summary "Added refund submission"
```

Checkpoint runs diff review, status, verification, and logging, in that order. A failed or inconclusive check stops automatic publication. Fix and retry, or explicitly record the failure with `--verification <id> --verify fail`. Repeating the same completed content does not append another entry.

For an earlier verification run:

```sh
bash .agent/scripts/verify.sh run test
bash .agent/scripts/checkpoint.sh --verification <receipt-id> \
  --tool <tool> --area payments --summary "Added refund submission"
```

The receipt ID is in the first command's output. Input changes invalidate it. A bare `--verify pass` cannot replace execution evidence. `verify.sh check` refuses a receipt written by an earlier v6.3 checkout, because the receipt format gained a field. Run the check again.

Use `--verify n/a` for manual-only work, and `--verify fail` when reporting failed work without a usable receipt. Committed changes need no flag after a first checkpoint. Use `--base <ref>` for the first one, or to review another range. Add `--node-only` for an explicit node write hidden by Git ignore rules. That flag refuses to skip outstanding product changes.

## Maintenance policy

`checkpoint.conf` defaults to `POLICY=strict`. It blocks actionable status findings. `POLICY=completion` defers size-only maintenance and continues to block structural defects. Informational tool availability does not block either policy.

Review candidates remain advisory. The agent must judge catalog relevance and test adequacy. Scripts cannot decide whether knowledge is durable or whether a source directive represents user intent.

## Finish migration

After reconciliation, run from the source checkout:

```sh
bash scripts/node.sh finalize "$project"
```

Finalization checks node structure. Run the configured project check separately to confirm the driver works. Keep the migration pending while structural repair findings remain.

The version migration creates a backup unless the node uses `track-all`. Preserve that backup and the project's Git diff during the trial. Runtime state and receipts stay outside loaded context, in the worktree's self-ignored `.agent/.state` directory.

## Workers and skills

Workers write lessons (learned rules and memory facts) through the node's writers. The session-log entry and `checkpoint.sh` are the orchestrator's. An orchestrator whose workers run in their own checkouts merges each worker's node back with `absorb.sh`:

```sh
bash .agent/scripts/absorb.sh mark "$worker"                      # in the worker's checkout, at dispatch
bash .agent/scripts/absorb.sh records --from "$worker"           # in the main checkout, when each attempt ends
bash .agent/scripts/absorb.sh docs --from "$worker"              # when the worker's code is integrated
```

See [absorb.md](absorb.md) for what applies and what is reported as a conflict.

A worktree whose `.agent` is a symlink to the node of another checkout of the same repository shares that node. Its writers write the shared files under the node's locks and wait up to `DA_LOCK_WAIT_SECONDS` (default 10) for a held one. `absorb.sh` reports `shared` for such a worker and merges nothing. Other symlinked nodes are refused.

In generated mode, `status.sh --load` lists the index pages to open. `index.sh ensure` is the orchestrator's call.

[worker-contract.md](worker-contract.md) states what an orchestrator may rely on: the bootstrap call, its output shape, the commands a worker may run, and what stays stable. From the source checkout, `bash scripts/node.sh describe "$project"` prints the same for one node as `KEY=value` lines.

Retiring a learned rule names what now enforces it: `learn.sh retire <id> --expected <version> --enforced-by <path>`.

Install skills at `.agents/skills/` and link `.claude/skills` to it for Claude Code ([tools/skills/README.md](../../tools/skills/README.md)). An update moves skills a node kept at `.agent/skills/`.

## Doc drift

`docs.sh check --name <file>` stamps a routed doc after its cited code is re-read. `links.sh` then reports `STALE:` for every cited project path changed, removed, or renamed in a commit after the stamp. A doc with no stamp is not checked.
