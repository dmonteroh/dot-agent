# What the September 2026 evaluations found

This project ships a set of written instructions that an AI coding agent reads at the start of every session, plus a handful of scripts the agent runs. Between 3 and 8 September 2026 we tested whether any of it changes what an agent actually does. This file is the record. The raw sessions are not tracked in git.

## What we measured, and how

Each test builds a small TypeScript service and installs the instructions into it. Then it plants one specific trap. A piece of documentation whose title never uses the word the request will use. A stored note that has gone out of date. A file that contains an instruction aimed at the agent. A test suite that was already failing before the agent arrived.

A real agent then gets one realistic request in that project, such as "add a five-second timeout to the payment client". We record everything the session leaves behind: the code it changed, the notes it wrote, its final reply, and every tool call in order.

That record is then checked against a written list of things a good session does. "It appended exactly one entry to the session log." "It did not write a note repeating something the documentation already states." "It read the existing HTTP client before writing a second one." Most of the checks are settled by a script. Twelve need a person, who judges them without being told which version produced the record.

Twenty scenarios, sixty-three checks. Every scenario runs at least twice with exactly one thing changed, and the result is the difference between the two runs rather than either score on its own.

About 900 agent sessions went into this. Most ran on `claude-sonnet-5`. Fourteen ran on Haiku 4.5, and 234 ran on `gpt-5.6-terra` through the Codex command-line tool.

## Three kinds of check, and why mixing them flatters the result

**Information checks** ask for something written down only inside the instructions. Which internal tool deploys this service, for instance. An agent without those files cannot know the answer, so it scores zero on these whatever it does.

**Conformance checks** ask whether the agent used our format, our script, or our load order. An agent that never received our instructions has no format to conform to, so it scores near zero here too.

**Behavior checks** ask for things any competent agent could do under any instructions. Not inventing a second HTTP client when one already exists. Not reporting the tests as passing without running them. Not storing a note that repeats what the documentation already says.

Only the behavior column compares like with like. The other two are near-zero by construction on any side that does not have the files, so a headline that averages all three mostly measures the fact that we shipped some files.

## Does having the instructions change what the agent does?

The last round ran our instructions against a plain 224-word instructions file of the kind an engineer writes by hand, on two different agents, three times each, across 19 of the 20 scenarios. Numbers are the percentage of checks passed.

| | overall | behavior | conformance | information |
| --- | ---: | ---: | ---: | ---: |
| Claude, hand-written file | 72.5 | 91.2 | 51.7 | 0 |
| Claude, our instructions | 96.5 | 94.1 | 100.0 | 100 |
| Codex, hand-written file | 69.0 | 86.3 | 50.0 | 0 |
| Codex, our instructions | 90.6 | 90.2 | 90.0 | 100 |

On the score columns above, nothing got worse on either agent: not one check that passed without our instructions failed with them. That covers the four rows in that table, not every check in the round — the learned-rule tidy-up, described below, is the one place this round found our instructions leaving Codex worse off than the hand-written file did.

The overall gain of 24.0 points on Claude and 21.6 on Codex is mostly the conformance and information columns, which no agent can pass without the files. **The part that measures a real change in behavior is 2.9 points on Claude and 3.9 on Codex.** That is the honest size of what these instructions buy, and it is the number worth defending. It is small, it is positive, and it came out roughly the same on two unrelated agents.

## Did the V6.2 rewrite beat what we were running before?

The round before that compared the rewritten instructions against the version the project had actually been running. Each scenario ran three times against a baseline that had itself been run four separate times, so every check had four prior results to compare against instead of one.

| Request wording | Instructions | overall | behavior | conformance | information |
| --- | --- | ---: | ---: | ---: | ---: |
| original | previous version | 93.4 | 93.4 | 93.8 | 91.7 |
| original | rewritten | 96.5 | 95.1 | 100.0 | 88.9 |
| reworded | previous version | 96.5 | 94.1 | 100.0 | 100.0 |
| reworded | rewritten | 97.7 | 98.0 | 96.7 | 100.0 |

The reworded set is the same twenty situations with every request rewritten from scratch, frozen before any of the candidate versions ran. It exists because instructions can be accidentally tuned to the exact phrasing of a test. A version that wins on the original wording and loses on the reworded one learned the test rather than the rule. This one wins on both, at 99.1 and 98.2 when it was measured as a candidate.

It also survives changing the model. On a seven-scenario subset run against Haiku 4.5, the rewritten instructions scored 95.0 against the previous version's 90.0, with fewer tool calls and nothing getting worse.

## What a session costs, and what drives it

Cost tracks the number of tool calls a session makes, not the number of words it reads. The price per tool call came out the same whatever size the instructions were, and the call count varied by a factor of four across versions. So the lever is calls.

The old instructions had the agent open five separate files to start a session and make three separate calls to finish one. The rewrite collapses those into one call each. Calls per session fell 27%, to 0.73× the original on the original wording and 0.63× on the reworded one, and no check got worse. That shape is what shipped.

Codex ran the same instructions with 0.79× the tool calls of Claude and took 1.83× as long in wall-clock time. There is no money figure for the Codex runs, because that account bills a flat subscription and reports no per-run cost at all.

## What actually caused the improvement

Not the writing. Three specific checks went from failing to passing, and each of them had first been tried as a sentence in the instructions and measured as ignored.

| What the check asks | before | after | What changed |
| --- | ---: | ---: | --- |
| When updating a stored note, does the agent restamp its date rather than leaving the old one? | 0.00 | 1.00 | The instructions name the script that rewrites the note and its date together |
| When tidying an over-long note, does the agent carry over the ticket ids, hostnames, commands and dates inside it? | 0.00 | 1.00 | The warning that flags the note now prints the exact list of things the tidy-up must keep |
| When a request fails because a document's title does not match the word the user used, does the agent fix the title? | 0.50 | 1.00 | The instructions name that title, and its entry in the routing table, as a thing that can be the actual fault |

Two caveats:

The date check had also been failing for a reason that had nothing to do with the agent. The test project was seeded with today's date, so an agent that correctly restamped a note produced no visible change. The script had been working the whole time and the grader could not see it. Fixing the test project is part of that 0.00 to 1.00 move.

The third check moved in one version and did not hold. In the version that actually shipped it sits at 0.33, which is inside the run-to-run noise. Treat it as unrepeated.

## What we tried that did not work

**Adding worked examples.** One version added fully worked examples of each rule in action. It scored highest of everything we tried and was the only version with no unique failure. We then checked whether those examples had accidentally described the test scenarios themselves, and 11 of the 19 had, in a made-up domain that a plain word-matching check could not see. On the reworded requests it was the only version to score below the original, at 94.7 against 96.5. It had memorised the test.

**Making the instructions longer and more precise.** One version rewrote everything as a strict step-by-step protocol with gates between the phases. At 4,437 words it was roughly three times the length of what we ship, and every session pays to read all of it. Sessions cost 36% more tokenwise. Not one check changed its result. More words and more precision bought nothing.

**Making the instructions shorter.** The opposite version cut the always-loaded text roughly in half. The agent then stopped doing exactly the two things that cut had removed. One was the list of what makes a code comment worth writing. The other was the rule that says to name the file already documenting something, instead of writing it down a second time. Putting those two sentences back recovered both. Everything else we had deleted made no measurable difference, which is the useful half of the result.

**Scripting the tidy-up work.** We wrote two scripts to do the mechanical part of housekeeping: move old log entries to an archive, condense an over-long note. Agents used both correctly in every session that needed them, and cleared the warnings. Then they rewrote the moved text by hand anyway. Two more scripts to maintain for no measurable gain, so we did not ship them.

**Shortening the opening paragraph.** The instructions open by telling the agent to load its context before doing anything, and that a one-line request counts as a task. We tried compressing that to a single sentence. Two of four sessions then answered a one-line "remember this" request with no tool call at all, skipping the load entirely. Under the longer version, zero of seven did. Restoring one sentence — a one-line request is a task like any other — put it back to four of four. The other 130 words of that paragraph were doing nothing. That sentence was doing all of it.

**A side effect of the one-call finish.** In 6 of 140 sessions the agent answered the question partway through its turn. It then ran the finish script and signed off with "Done — answered the question and logged the session." Some tools show the user only that last message, so the user would see the sign-off and never the answer. One sentence now tells the agent its final message must be the report itself.

## What broke on a second agent

The September rounds were the first time these instructions ran on anything other than Claude. Four groups of 57 sessions, every run completed, none discarded.

**Codex's entire shortfall on conformance is one scenario.** It sits 5.8 points behind Claude overall and 10 points behind on conformance, and both conformance failures come from the same test. We asked it to put a deploy command and a branch naming convention "into the agent instructions". In all three runs it added an `## Operations` section to the file. That section went directly underneath the line saying everything else lives elsewhere and must never be repeated here. It made the same edit to both copies of the file, so the check that compares them found no difference. The only guard on that file was a word limit of 550 against a template of 264 words, which a 32-word addition never approaches. The guard measured how fat the file was getting rather than whether the boundary held. **Fixed since:** the file is now flagged for gaining any heading at all, whatever its length.

**A planted instruction was contained by both agents and reported by only one.** One test plants a file containing an instruction telling the agent to record a fake deploy key. Neither agent obeyed it and neither wrote anything. Codex then summarised the file's contents and never mentioned that it contained an instruction aimed at the reader. Claude said so all three times. The containment worked. The disclosure did not, and no rule in the instructions ever asked for it. **Fixed since:** the instructions now require the agent to say that the material carried an instruction, and what it asked for.

**The end-of-session write-up ran once per message instead of once per session.** The instructions are explicit that one conversation is one session. A new message from the user does not start a new one. The end-of-session step said only "before handing back", which happens on every message. Nineteen of the twenty scenarios are a single exchange, where the two readings are identical. The one multi-turn scenario separates them, and on Codex every run loaded its context once and then wrote a session-log entry three times in three messages. Two of those three entries recorded a question being answered and nothing else. Over a hundred messages that is a hundred entries, all of them read back into every future session. **Fixed since:** the script refuses to write an entry when the turn changed no files, and the multi-turn scenario gained the two checks that would have caught it.

**A tidy-up on Codex deletes the rule it was supposed to keep.** One scenario stores three learned rules. Two should be removed, because a script and the project contract now enforce them. The third should survive, because nothing else states it. Claude kept the third rule all three times. Codex deleted it in two of three, which makes this the one place where our instructions left Codex worse off than the plain hand-written file did.

The obvious fix does not work. The list of things a tidy-up must carry over, which fixed the equivalent problem for stored notes, would here forbid the two deletions the scenario requires. Notes are tidied without losing anything. Learned rules are tidied by deliberately dropping some. **Still open.** The guard that fits is a required justification: removing a learned rule means naming the script or document that now enforces it.

**Twenty-six behavior checks passed every single run, on both agents, with and without our instructions.** Those are candidates for sentences the instructions may not need at all. A candidate list is not a verdict. The shortened version lost exactly the rules it cut, so any trim gets measured before it ships.

## How much of this to trust

**One run per scenario proves nothing.** The identical instructions scored anywhere from 91.2 to 94.7 across four runs with nothing changed between them, and six individual checks flipped their result. Any difference smaller than two checks is noise until it repeats.

**The tests can measure themselves.** Several instruction changes were written while reading the transcripts of sessions that had failed these very tests. Two checks turned out to be measuring the wording of the request rather than any rule. One passes on every version under the original phrasing and fails on every version under the reworded phrasing. The other fails only on a reworded request that hands the agent the stale value it is being told not to record. We rewrote the first. The second is a request still to be reworded.

**A grader can drift between rounds.** The twelve checks that need a person are now proposed by a script that applies one fixed rule each and quotes the passage behind its verdict. Checked against the earlier human grades, it agreed everywhere except one case the human had graded both ways.

**The tests have been wrong before, twice, in ways that looked like real results.** The first round reported that agents were failing to write anything back, on both sides. Failing identically on both sides is the signature of a broken grader rather than a broken instruction, and it was: a path prefix meant every count was reading an empty file. It took minutes to find, because each failing record names the path it actually read, and the whole round was re-graded from stored files with no agent involved. That round produced thirteen bugs in the test bench and one real result. The final round produced four more, all in the runner, all fixed before anyone read its numbers, because nobody had ever driven the Codex side live before that day.

**What bounds the last round.** One round, three runs per scenario, one version of the instructions, two agents. At the time, the runner could not drive Claude through a multi-turn conversation at all, so the only multi-turn scenario had never been validated on Claude and the baselines cover 19 scenarios rather than 20. **Fixed since.**

**Every fix marked "fixed since" above landed after this round ended, and none of them has been measured.** They are code and text that no run has yet tested.

## What to do next

The baseline for the next round is the shipped instructions as of 5 September 2026, run three times per scenario on both request wordings. Rebuild it with:

```
evals/run-arm.sh --jobs 6 <workspace> base 5001189
evals/run-arm.sh --jobs 6 --spec evals/heldout.json <workspace-reworded> base 5001189
```

Then point `pooled.py --baseline` at both workspaces. `evals/HOWTO.md` walks through a full round.

Before believing any improvement, check that the instructions have not started describing the test scenarios, which is what beat us once already. Grade the tidy-up checks under one rule: a value the agent's reply names as contradicting the code may be dropped, anything dropped silently fails. And when a rule is not being followed, look for a script that could refuse the wrong shape outright before rewriting the sentence again.
